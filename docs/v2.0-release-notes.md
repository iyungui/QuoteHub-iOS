```swift
// ViewModifier로 재사용성 극대화 (CustomProgressView.swift)
struct ProgressOverlay<VM: LoadingViewModel>: ViewModifier {
    @ObservedObject var viewModel: VM
    
    func body(content: Content) -> some View {
        content
            .overlay {
                if viewModel.isLoading {
                    CustomProgressView(message: viewModel.loadingMessage)
                        .transition(.opacity)
                }
            }
    }
}

extension View {
    func progressOverlay<VM: LoadingViewModel>(viewModel: VM) -> some View {
        self.modifier(ProgressOverlay(viewModel: viewModel))
    }
}
```

## **핵심 기술 도전과 해결**

#### **문제 발견**
문장모아는 1.0 버전을 설계했을 당시 북스토리를 fetch를 할 때, 모든 사용자의 공개된 북스토리 불러오기, 특정 사용자의 북스토리 불러오기, 그리고 자신(인증된 사용자)의 북스토리 불러오기로 나누어서 설계했습니다. 

이 때 뷰코드도, 네트워크 요청 코드도 모두 중복이 되는 코드가 많았기에, **enum으로 LoadType을 설계하고 딕셔너리로 `var bookStories: [LoadType: [BookStory]]` 이렇게 설계**했습니다. 즉 public bookstories viewmodel, my bookstories viewmodel, friend book stories viewmodel을 따로따로 만들지 않고, **하나의 북스토리 뷰모델로 만드려는 시도**를 했습니다.

#### **문제 발생**
여러 화면이 이 하나의 ViewModel을 공유했는데, `currentPage`·`isLoading`·`currentStoryType` 같은 **페이지네이션 상태도 한 곳에서 공유**되고 있었습니다. 그래서 화면을 오갈 때 **로드가 누락되거나, 페이지가 꼬이거나, 한 타입의 응답 콜백이 진행 중이던 다른 타입의 상태(currentPage/isLoading)를 덮어쓰는** 문제가 발생했습니다.

#### **어떤 종류의 문제였나 (정확히)**
응답 처리는 모두 메인 스레드(`DispatchQueue.main.async`)에서 이뤄졌기 때문에 **메모리를 동시에 건드리는 data race는 아니었습니다**. 정확히는 **여러 화면이 하나의 공유 가변 상태를 시점에 따라 다르게 갱신해 결과가 타이밍에 좌우되는 logical race(상태 충돌)** 였습니다. 이런 종류는 TSan으로 잡히지 않아, 화면 전환 시 데이터가 섞이는 **증상으로 발견**했습니다.

#### **해결 과정**
원인이 "상태를 한 ViewModel에 몰아넣은 것"이라고 보고, **public / my / friend 북스토리를 각각 독립된 ViewModel로 분리**해 페이지네이션 상태(currentPage·isLoading 등)를 서로 **격리**하고, 각 ViewModel을 **`@MainActor`로 두어 상태 변경을 메인에서 직렬화**했습니다. 즉 핵심 해결책은 **공유 가변 상태 제거 + @MainActor 격리**입니다.

```swift
// 화면별로 상태를 격리한 독립 ViewModel (@MainActor) — PublicBookStoriesViewModel.swift
@MainActor
@Observable
final class PublicBookStoriesViewModel {
    var bookStories: [BookStory] = []
    private var currentPage = 1
    private var loadingTask: Task<Void, Never>?
    // my / friend 도 각각 자신의 상태를 별도로 보유 → 서로 덮어쓸 공유 상태가 없음
}
```

> 토큰 갱신에서 발생한 또 다른 동시성 문제는 **Actor 기반 single-flight**로 해결했습니다 — 아래 *인증/보안* 섹션 참고.

### **역할과 책임 분리 (아키텍처)**
화면별로 ViewModel을 분리하면서, 공통 동작(목록 로드·새로고침·페이지네이션)은 **protocol로 추상화**해 중복을 줄이고 일관된 인터페이스를 유지했습니다. (읽기 전용과 CRUD를 프로토콜 상속으로 구분) 

```swift
// 프로토콜 기반 역할과 책임 분리 (BookStoriesViewModelProtocols.swift)

// 기본 읽기 전용 프로토콜
protocol BookStoriesViewModelProtocol: LoadingViewModel {
    var bookStories: [BookStory] { get }
    func loadBookStories() async
    func refreshBookStories() async
}

// CRUD 확장 프로토콜 (내 뷰모델만)
protocol EditableBookStoriesViewModelProtocol: BookStoriesViewModelProtocol {
    func createBookStory(...) async -> BookStory?
    func updateBookStory(...) async -> BookStory?
    func deleteBookStory(storyId: String) async -> Bool
}

typealias ReadOnlyBookStoriesViewModel = BookStoriesViewModelProtocol
typealias EditableBookStoriesViewModel = EditableBookStoriesViewModelProtocol
```

### **Swift Concurrency 전면 도입**
**이번 리팩토링에서 가장 중점적으로 개선한 부분 중 하나는 Swift Concurrency(async/await, Task, TaskGroup)을 적극적으로 도입한 것입니다.**

기존 1.0 버전에서는 completion Handler와 Result 타입을 사용하여 비동기 작업을 처리하고 있었는데, 네트워크 요청이 많아질수록 코드의 중첩이 증가하고 흐름을 파악하기 어려워지는 문제가 있었습니다.
따라서 이번 리팩토링에서는 **async/await 기반 구조로 전환하여 비동기 로직을 동기 코드처럼 읽을 수 있도록 개선하는 것을 목표로 했습니다.**

#### **네트워크 레이어 통합**
Swift Concurrency를 적용하기 전, 먼저 네트워크 계층부터 정리했습니다. 기존에는 각 서비스 파일마다 AF.request 호출 및 응답 처리 로직이 반복적으로 작성되어 있었고, 동일한 네트워크 코드가 여러 파일에 분산되어 있었습니다.

이를 해결하기 위해 APIClient.swift를 중심으로 네트워크 요청을 처리하도록 구조를 재설계했습니다. **URLSession 기반의 공통 제네릭 요청 메서드와 JSON 파싱 로직을 구현하여 네트워크 요청 코드를 일원화 했고, 각 Service는 필요한 엔드포인트와 모델만 정의하도록 역할을 분리했습니다.**

이를 통해 네트워크 레이어의 중복 코드를 제거하고, async/await 기반의 간결하고 가독성 높은 구조로 리팩토링할 수 있었습니다.

#### **TaskGroup을 활용한 동시성 기반 데이터 로딩 최적화**

- 특히 **앱을 처음 실행할 때 (LaunchScreen이 잠깐 나타날 때) 사용자 프로필, 북스토리, 테마, 인증상태 확인 등 여러 데이터를 모두 불러올 필요가 있었습니다.

초기 1.0 버전 구현에서는 단순히 각 로드 작업을 순차적으로 await 하여 실행했습니다.
저는 이번 리팩토링에서, 각 요청이 서로의 결과에 의존하지 않는 독립적인 네트워크 요청이라는 점에 주목했습니다. 따라서 특정 요청이 완료될 때까지 기다릴 필요가 없었고, TaskGroup을 사용하여 여러 작업을 동시에 시작함으로써 전체 초기 로딩 시간을 단축할 수 있었습니다.

이를 해결하기 위해 TaskGroup을 사용하여 여러 작업을 동시에 시작하도록 설계했습니다.(TaskGroup은 여러 Child Task를 생성하여 동시성을 제공하며, 각 작업은 Swift Runtime에 의해 효율적으로 스케줄링됩니다. 따라서 네트워크 응답을 기다리는 동안 다른 작업이 진행될 수 있어 전체 초기 로딩 시간을 줄일 수 있었습니다.)

```swift
await withTaskGroup(of: Void.self) { group in
    group.addTask {
        await userViewModel.loadUserProfile(userId: nil)
    }

    group.addTask {
        await userViewModel.loadStoryCount(userId: nil)
    }

    group.addTask {
        await myBookStoriesViewModel.loadBookStories()
    }

    group.addTask {
        await myThemesViewModel.loadThemes()
    }
}
```

또한 Swift Concurrency는 Task를 효율적으로 알아서 스케줄링하여 네트워크 대기 시간 동안에 다른 작업을 수행할 수 있도록 하는 구조라는 점도 이해할 수 있었습니다.

> 이후 런치 초기 로딩처럼 **동시에 실행할 작업 개수가 고정**된 경우에는 TaskGroup 대신 **`async let`** 으로 교체했습니다. 고정 개수에는 async let이 더 간결하고 의도가 명확하기 때문입니다. (개수가 런타임에 가변일 때는 TaskGroup을 사용합니다.)

```
private func loadPrivateData() async {
    async let profile: Void = userViewModel.loadUserProfile(userId: nil)
    async let count:   Void = userViewModel.loadStoryCount(userId: nil)
    async let stories: Void = myBookStoriesViewModel.loadInitialIfNeeded()
    async let themes:  Void = myThemesViewModel.loadThemes()
    _ = await (profile, count, stories, themes)
}
```

### **인증/보안 — Sign in with Apple + JWT + Keychain**

#### **로그인 흐름**
Sign in with Apple로 로그인하며, 클라이언트는 애플이 발급한 **1회용 authorizationCode**만 백엔드로 전달합니다. 실제 애플 토큰 교환(client_secret 사용)은 서버에서 수행하고, 서버는 검증 후 **자체 JWT(Access / Refresh Token)** 를 발급합니다. 클라이언트가 비밀키를 갖지 않는 표준 서버사이드 플로우를 따랐습니다.

#### **토큰 관리 — 2-토큰 + Keychain**
- **Access Token**: 매 요청 헤더에 첨부하며, 짧은 수명으로 탈취 시 위험 창을 최소화합니다.
- **Refresh Token**: Access 만료 시 갱신에만 사용하고, 매 요청에 노출되지 않으며 서버에서 폐기할 수 있습니다.
- 두 토큰 모두 **Keychain**에 `.whenUnlockedThisDeviceOnly` 옵션으로 저장했습니다. (잠금 해제 상태 + 이 기기에서만 접근. UserDefaults는 평문 저장이라 자격증명에 부적합)

#### **401 자동 토큰 갱신 인터셉터**
APIClient에서 응답이 401일 때 Refresh Token으로 Access Token을 자동 갱신한 뒤 원래 요청을 1회 재시도하도록 구현했습니다. `isRetry` 플래그로 무한 재귀를 차단했습니다.

#### **트러블슈팅 — Task.detached로 인한 순서(ordering) 문제**
로그아웃·회원탈퇴 시 토큰 삭제를 `Task.detached { ... }`로 분리하고 곧바로 화면을 전환하도록 구현했었는데, **토큰 삭제 완료를 기다리지 않고 상태가 먼저 바뀌는 순서 문제**가 있었습니다. 또한 `try?`로 삭제 실패가 은폐되어, 삭제에 실패하면 토큰이 남아 다음 실행 시 의도치 않은 자동 로그인으로 이어질 수 있었습니다.

원인을 분석하면서 **Keychain 작업은 본래 동기 API**라는 점을 확인했고 `Task.detached`가 애초에 불필요했음을 알게 되었습니다. 토큰 삭제를 **동기 호출로 바꿔 화면 전환 전에 완료를 보장**하고, do-catch 문을 적용하여 실패 시 디버깅 로그를 추가했습니다.

> 이 경험을 통해 "백그라운드 실행"과 "완료 순서 보장(await)"이 별개의 문제라는 것, 그리고 동기/비동기 선택 기준을 명확히 이해하게 되었습니다.

#### **트러블슈팅 — 동시 토큰 갱신(thundering herd) 방지**
앱 실행 시 여러 데이터를 TaskGroup으로 동시에 불러오는데, 이때 Access Token이 만료된 상태라면 **여러 요청이 거의 동시에 401을 받아 각자 토큰 갱신을 시도**하는 문제가 있었습니다. 동일한 갱신 요청이 중복 발생했습니다.

원인은 네트워크 계층(APIClient)이 갱신 동작을 직렬화하지 않는다는 점이었습니다. 동시에 6개의 요청이 갱신을 트리거하면 실제 갱신이 6번 실행되는 것을 break-point와 print 로그로 확인했습니다.

이를 **single-flight** 패턴으로 해결했습니다. 진행 중인 갱신 작업(Task)을 actor에 보관하고, 첫 요청만 실제 갱신을 트리거하며 나머지 요청은 그 Task의 결과를 기다려 공유하도록 했습니다. 그 결과 동시에 여러 요청이 401을 받더라도 **실제 토큰 갱신은 한 번만** 실행되도록 했습니다. (6개 동시 요청 → 갱신 1회 확인).

이 과정에서 actor의 **재진입(reentrancy)** 특성 때문에 단순 플래그로는 막을 수 없어 "진행 중인 Task 자체를 체크"해야 한다는 점, 그리고 갱신 엔드포인트가 인증을 요구하면 자기 자신을 기다리는 교착에 빠질 수 있다는 점까지 이해하게 되었습니다.
